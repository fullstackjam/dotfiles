# Ship a PR

统一 GitHub PR 的交付流程，项目差异从目标仓库读取，不在这里复制。
用户说“MR”但目标是 GitHub 时仍使用 PR；遇到其他托管平台时说明本 skill
只覆盖 GitHub，再按该平台的工具和仓库流程处理，不套用 `gh`。

## 确定目标与终点

- 根据用户指定路径、当前任务改动和已有 PR 确认仓库。多个仓库同时打开不代表
  全部都要提交；确实无法判断时才询问目标。涉及多个仓库时，为每个仓库分别记录
  根目录、remote、base、head、PR 和验证结果，并在对应目录执行命令。
- 读取该仓库适用的 `AGENTS.md`、贡献说明、PR 模板及审查/部署规则。
  不将个人目录路径写入仓库，也不假定所有项目都用相同测试、分支名或合并方式。
- 用户直接调用 `$ship-pr`（包括只发送 skill 链接）时，默认授权当前任务完成
  创建 PR → CI → 完整审查 → 修复 → 合并 → 清理，不在 PR 创建后结束。
  例如，修复后只发送 `$ship-pr` 应继续到合并；`$ship-pr，只开 PR，先别合并`
  则停在创建阶段。明确的范围限制始终优先，草稿请求保持草稿。
- 未直接调用 skill 的普通“开/提 PR”请求做到创建或更新 PR；“合并/落地/ship it”
  按合并终点执行。已授权合并时，完成 CI 和审查后直接合并，无需重复确认。
  已有授权持续有效；调用 skill 本身不增加部署、生产数据或跨仓库修改授权。
- 当前用户明确要求直接提交默认分支时，遵循该指令和仓库允许的流程，不强加 PR；
  不绕过服务端保护规则。发布标签使用仓库的发布流程。

## 准备与提交

1. 检查工作区、暂存区、分支、remote 和已有 PR。只暂存本次任务的文件或 hunks；
   不用 `git add -A` 混入其他任务。不要切换或清理其他任务正在使用的 worktree。
2. 已有 PR 使用它实际的 base/head；新 PR 优先遵循用户指定的目标，否则查询远程
   默认分支，不能回退猜测 `main`。获取最新远程引用后，以远程 base 比较完整改动。
3. 请求 PR 而当前位于默认分支时，创建适当的功能分支；存在并行任务时使用独立
   worktree。保护已有未提交改动，不为整理分支丢弃或搬走其他任务的文件。
4. 按仓库要求执行必要验证并提交本次改动。已完成且覆盖当前版本的检查不重复跑；
   已安装 hooks 会执行的检查不无故重复，未安装 hooks 也不能略过仓库规定的验证。
5. 推送到确认过的 remote/head，复用该分支已有的开放 PR，避免重复创建。
   遵循仓库的标题和提交规范；PR 正文采用仓库模板，写清结果和实际验证。
   使用结构化参数或临时文件配合 `--body-file`，保留真实换行。

## CI 与完整审查

终点仅为创建 PR 或草稿时，报告链接和已知检查状态；直接调用 `$ship-pr` 的默认
流程及其他已授权合并的请求继续以下步骤。CI 排队或运行中属于待完成工作，继续
在当前会话跟进；只有无法自行解决的阻塞才报告阻塞并交还用户。

- 等待当前 PR head 的必需检查。结合服务端保护/rulesets 和仓库检查清单判断要求，
  不把“尚未注册检查”当作通过，也不假定所有显示的检查都是必需的。
- 必需检查失败时读日志：本次范围内、解法明确的问题自行修复、提交、推送并重新
  验证；产品行为、范围、迁移或上线策略的取舍交给用户。权限、人工审批或环境故障
  无法自行解决时报告具体阻塞，不反复重跑同一失败或绕过门禁。
- 审查当前 PR 的完整 diff，读取相关上下文、已有评论和正式 reviews；有适用的
  项目审查 skill 时使用它。关注行为、设计、测试、兼容性及回滚风险。CI 通过不能
  替代审查；本地审查也不能替代仓库要求的人工 approval。
- 明确的问题在范围内修复，更新后重新检查完整 diff 和 CI。需要用户选择时给出
  具体位置、影响和选项。每次 head 变化都会使旧版本的审查/检查证据失效。

## 合并与收尾

- 已有合并授权、当前 head 的必需检查通过且审查无阻塞时，直接合并。
  合并前重新核对 PR head；可用时用 `gh pr merge --match-head-commit <sha>`
  限定为已审查提交。合并方式遵循仓库配置和约定，不写死 squash。
- 默认在当前会话完成合并，不启用 `--auto`。用户明确要求 auto-merge 时，先完成
  审查，再按授权设置；报告此时是等待自动合并还是已经合并。后续新增提交需要重新审查。
- 不使用 `--admin` 绕过保护，不自行 force-push 或 amend 已推送提交。
  未满足的人工 approval、未解决的讨论或权限要求应作为阻塞报告。
- 查询并确认实际合并结果后，按仓库规则清理本次创建的分支和 worktree。
  不假定 `--delete-branch` 已切换分支或完成本地清理；先检查工作区是否干净、分支
  是否被其他 worktree 使用。只在安全且属于本任务的 checkout 中做 `pull --ff-only`。
- 仓库合并会触发部署时，区分合并结果与部署结果；仅在已授权的交付范围内跟进。
  未验证部署就明确说明，不自行回滚生产或修改 secrets。
- 最后给出各仓库的 PR 链接、创建/合并状态、验证依据和未完成项。
