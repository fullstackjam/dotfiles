# 追溯原因与取舍

代码能证明当前做什么，不能单独证明作者当时为什么这样做。把用户给出的原因当成待查假设，与其他解释一起核实。

## 找到历史锚点

从目标文件、符号、配置键或当前 diff 开始。用相关行的 blame 找最后触碰的提交，再追实际引入和改变行为的提交；最后一次格式化不等于设计起点。

按问题选择命令，限定文件或行范围：

```bash
git blame -L <start>,<end> -- <file>
git log --follow -p -- <file>
git log -S '<symbol-or-value>' -- <file>
git show <commit> -- <file>
```

从提交内容和消息提取真实的 PR/MR、工单和文档线索，再读取正文及相关讨论。不猜编号，不只看标题，不把当前代码的合理性写成历史动机。

## 按证据缺口扩大

优先查现有线索能到达的来源。代码评审通常能说明实现时的取舍；工单说明需求；文档和聊天可能保留讨论；故障记录、日志和指标说明当时约束或当前是否仍存在。

通过当前可用的 connector、CLI 和领域 skill 访问，不能因没有 MCP 就认定该来源不可查。公司 GitLab、Jira、飞书和监控分别沿用对应技能的访问约定。通用技能不复制公司账号、集群或凭据规则。

原始记录足够回答时停止。不默认搜索全部系统、查询生产或启动多模型调查。相关来源不可用、检索为空或成本不值得时，说明具体缺口；空结果只证明本次没有找到，不证明没有原因。

## 保持证据强度

- **直接记录**：作者或当时资料明确说了原因，紧邻结论给引用。
- **证据支持的推断**：多项记录指向一个解释，写出推理和各自来源。
- **猜测**：当前材料只允许提出可能性，保留其他同样合理的解释。
- **未知**：说清查了什么、仍不能回答什么，不补造动机。

来源冲突时并列展示，考虑时间、版本和上下文，不挑能讲出完整故事的一条。历史约束与当前事实分开；当年的故障不证明今天还存在，今天测不到也不推翻历史记录。

## 交付

先回答问题，再给决定性的证据、推断和剩余缺口。只列实际咨询的来源及影响结论的未查范围，无需凑齐固定来源分类。

如果调查是删除或修改的前置，说明哪些行为仍需保留、哪些可改、哪些前提未证实。调查不自动授权改代码、建单、联系作者或发布；后续影响分析用 [blast-radius](../blast-radius/SKILL.md)。
