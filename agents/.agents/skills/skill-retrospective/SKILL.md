# 把经验落到技能

从真实问题找到最小有效改进，通常修改已有 skill；只有独立流程没有合适入口时才新增技能，不复制现有约定做一个总控 mode。

## 以发生过的事为证据

优先读当前对话、受影响 diff 和实际输出，区分执行错误、技能缺失/误触发、示例或环境问题。需要旧记录时用 [work-context](../work-context/SKILL.md) 锁定任务和范围，不遍历无关聊天。

针对每个候选指出：发生了什么、哪份证据支持、现有规则为何没有阻止、最小改进在哪里。不要把一次任务偏好提升成全局要求；已明确要求长期采用的选择可以记录，判断为反复模式则需要多次证据。历史资源和授权不写成当前事实。

## 选择能真正生效的落点

先看能否删掉错误路径、消除手工同步列表或复用现有类型/脚本检查。实际存在重复机械错误且收益足够时，才考虑补脚本、lint 或测试；不为假设风险引入新框架。

需要判断的经验再写进正文，说明适用条件和一个能区分对错的例子。只是 skill 没触发时优先修 description；资料过期则修唯一来源，不把一份手册复制到多个入口。

先找已有技能，读取其真正的源码、相关引用和调用方。个人、工作、项目来源各归原处；插件缓存和安装生成文件不直接修改。请求只是复盘时先交付建议；用户已经要求修改时完成获准部分，不重复确认。

## 控制范围和验证

按可用的 skill 创作规范编辑；普通规则、文案修改检查 frontmatter、diff、引用和受影响示例。新增或修改脚本时运行相关行为检查，不自动做多模型评估、全量回归或真实云操作。

验证失败先区分改动、用例和环境；修正后只重跑受影响项。不要为让检查通过放宽实际约束。确需扩大成本或复杂度时说明要消除的不确定性，由用户决定。

## 交付

给已采纳的改进、源码路径、对应问题和验证输出；被舍弃的候选只解释影响判断的原因。未验证行为明确标注，不能把文本校验通过写成实际任务效果已证明。

未处理事项留在当前回复或任务记录，不自动创建 backlog、发消息、开 PR 或提交其他仓库。用户明确要求 commit/push 时按当前仓库约定推进。
