# 核对性能结论

检查一条具体结论是否被数据支持。可以审查已有指标、实验脚本和结果，不要求先做新实验。

## 先确定要判断什么

把结论写成可核对的话：指标、单位、工作负载、比较对象、时间窗和决定。例如延迟要区分平均值与分位数，吞吐量要区分收到的请求与成功完成的工作。

说明什么结果会改变决定，以及现有数据足以回答到什么程度。没有依据时不承诺提速比例、节省工时或成本收益。

## 检查已有证据

按结论选择相关项，缺失的证据决定限制，不机械补齐所有实验：

1. **工作确实发生。** 请求到达目标、数据实际读写、异步任务被等待、结果被使用。排除未执行的惰性操作、缓存命中和静默 no-op。
2. **快不等于正确。** 核对成功/失败数、超时、重试、跳过量和输出正确性。失败很快时，总请求吞吐不是有效吞吐。
3. **两边口径可比。** 核对版本、构建模式、数据规模、并发、流量构成、连接池、批处理、事务、缓存冷热和资源限额。只比较了默认配置就说明比较对象，不宣称实现优劣。
4. **瓶颈有依据。** 用现有 profile、CPU、I/O、网络、锁或负载生成器数据解释限制；源码推测不能替代观测。说不清瓶颈时，不编造性能上限。
5. **结果没有超出可能收益。** 某段只占总耗时的 10%，只优化该段不能解释整体耗时下降一半。超出时先检查计时范围、缓存、错误和遗漏工作。
6. **变化超过噪声。** 单次只能支持单次观察。检查样本数、波动、机器负载和测量开销，不能把低于波动的差异当提升。
7. **对整体有意义。** 微观测试与端到端等待时间分开。局部变快不自动证明真实请求、批次或用户操作也变快。

指标采集沿用对应领域 skill，核对环境、标签、时间范围和来源。配置声明的 CPU/memory request 不等于实际用量，图上相关性也不证明原因。

## 确需补测时

先提出能消除哪个不确定性、在什么环境测、预计时间/负载和停止条件；需要扩大范围时由用户决定。读取已有结果不等于授权发压、扩容或改配置。

在已授权范围内，复用最小现成脚本，打印有效工作数和错误数。比较前后尽量交替顺序，让预热、缓存和环境漂移不偏向一边；根据噪声和成本选重复次数，不固定五轮。profile 的开销要与正式计时区分。

差异小于波动、连续尝试无新证据或已达到约定停止条件时结束，不持续试验直到出现好看的数字。

## 交付

先说提升、退化、无可测差异或证据不足。附单位、前后值、负载口径、样本数和波动，以及已观测到的限制；只写实际取得的信息。未找到瓶颈不掩盖可靠观测，但限制原因和推广范围。

给原始结果或可重复命令，明确未验证项。已有单次观察就如实标单次，不把没有测量的部分写成结论。
