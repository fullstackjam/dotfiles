# 解释当前运行机制

用源码、配置和必要的运行态证据建立能指导修改的理解。调查交付解释，不自动进入实现。

## 从一个具体问题开始

先确定用户要理解的行为和范围。含糊时根据当前对话、文件和改动给出合理解释并继续；只在缺少关键对象时询问。

从真实入口跟一次请求、事件、命令或配置变化，追到用户能观察的结果。明确途中由谁读取、转换、存储和写入状态，哪些分支决定结果。区分配置声明、生成产物和实际运行状态；源码有某路径不证明当前环境启用了它。

单模块问题直接查。跨仓或跨服务时按链路逐步展开，不默认全仓扫描、委派或固定模型。命中边界后，先找该环境已有的领域 skill、配置和访问工具，不在这里维护环境常量或新的认证方式。

需要回答历史取舍时转 [why](../why/SKILL.md)；需要判断改动会影响哪里时转 [blast-radius](../blast-radius/SKILL.md)。不为解释而执行写入、重启或发布。

## 核实链路是否完整

按问题选择需要看的证据，不把下面各项当作每次必跑的清单：

- 代码：调用入口、核心类型、状态所有者、外部边界、错误和重试路径。
- 配置：来源、覆盖优先级、生成和加载时机；文件或远端值变化后，进程何时使用它。
- 发布：提交、构建、镜像、版本回写、控制器同步和运行版本之间的实际衔接。
- 依赖：固定版本、本地补丁、序列化格式和消费者；不能凭熟悉的库名推断当前行为。

遇到矛盾回到相关源码或真实值，不靠扩大叙述消除矛盾。工具不可用时说明哪一段无法核实，保留其他可继续的调查。

## 交付

先用几句话说明核心机制，再给需要的运行流程、代码/配置落点和容易误解的条件。文件和符号只引用能帮助用户继续定位的部分，不逐行复述源码。

多组件交互确实难以用文字看清时画小图；简单问题无需图和固定章节。引用真实文件、提交或外部来源，把运行态未验证的部分标明。用户问的是技术放置或归属时，给出推荐位置及理由。
