# 组织技术文档

先确定谁会读、读后要做什么或理解什么，再安排材料。已有模板、受众、语言和范围要求优先，不为统一结构重写无关段落。

## 选一个主要用途

- **教程**：让初学者做出一个具体结果。每步给能看见的进展，前置条件齐全，原理只解释到够用。
- **操作指南**：帮助已有基础的人完成任务。给必要条件、操作、判断分支和成功结果，把背景链接出去。
- **参考资料**：供查参数、接口、限制和错误。按被描述对象组织，来源明确，未知处如实保留。
- **原理或设计说明**：解释机制、约束、历史原因和取舍，让读者能判断方案。

主用途指导安排，不强制一个文档只能含一种内容。短指南可附少量参数说明；只有混杂妨碍阅读、内容确有独立维护价值时才拆分。

## 写到读者能继续

操作步骤从目标命名，区分用户做什么、系统随后做什么、如何确认成功。警告和必要条件放在受影响操作之前。没有运行过的步骤或命令标明未验证，不能为填示例编造输出、链接或界面入口。

介绍陌生工具时，用一两句话说明用途和当前步骤。不把内部仓库、凭据实现、控制器细节塞进使用流程，除非它们影响读者的实际选择。运维和发布文档分清提交、合并、构建、部署和业务验收。

解释使用真实机制，必要时给小图和真实符号；不要用一串抽象名词代替过程。原理和取舍不明时按需用 [how](../how/SKILL.md) 或 [why](../why/SKILL.md)，不因写作自动扩大调查。

## 保留语义与格式

明确主体和动作，让限定词靠近它修饰的对象。同一事物保持一个名字，保留项目原有命令、参数、大小写和代码缩进。长度、标点和句式服务清晰表达，不按英语词数规则修改中文。

保持事实、时间、范围、否定、归因和确定程度。缺数字就不用数字，不把主观反馈改成性能事实。不把代码、路径、链接目标或受保护的格式当作 prose 润色。

措辞编辑按语言使用 [humanizer](../humanizer/SKILL.md) 或 [humanizer-zh](../humanizer-zh/SKILL.md)，不重复维护同一套模式。写 Wiki、周报或其他有领域规范的内容时，保留对应技能的双语、归期、字数和写入要求。

## PR/MR 与提交说明

先说具体问题和改后行为，必要时给触发条件或前后例子。再说明影响、实际取舍和验证。简单变更可以一两句，不强制固定标题和多段目录；服从仓库模板和 commit 规范。

让未看过聊天的人能审查，不复述调试过程。代码形态、CI 通过、部署和业务验证分别按真实状态表达，详细日志链接到证据。

## 交付检查

核对读者能否从文档确定前提、下一步和成功结果，链接是否指向实际内容，改写是否保留语义。小改只检查受影响段落、引用和示例。起草不包含发布、外发或向远端文档写入。
